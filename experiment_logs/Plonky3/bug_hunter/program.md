## Context

Plonky3 is the arithmetic backend for multiple ZK provers (leanMultisig, SP1, Pico).
Field arithmetic bugs here propagate to every downstream prover. A wrong multiplication
in BabyBear corrupts every polynomial commitment that uses it.

Key fields:
- **BabyBear** — p = 2^31 - 2^27 + 1 = 2013265921
- **KoalaBear** — p = 2^31 - 2^24 + 1 = 2130706433
- Both use the `Monty31` generic (Montgomery representation)
- SIMD acceleration via `PackedMontyField31` (AVX2=8 lanes, AVX-512=16 lanes)

Key transforms:
- `Radix2Dit` / `Radix2DitParallel` — NTT/INTT for polynomial evaluation
- Coset LDE — low-degree extension for FRI
- Twiddle factor precomputation

## Severity Classification

- **Critical** — Wrong field arithmetic that silently produces incorrect proofs.
  The verifier might still reject (safety preserved), but the prover is broken.
  If the verifier ALSO accepts the wrong proof, it's a ZK soundness bug.
- **High** — Correctness bug that triggers under specific but plausible conditions
  (certain field sizes, certain polynomial degrees, edge-case inputs like 0 or p-1).
- **Medium** — Bug that only triggers under adversarial inputs or extreme parameters
  unlikely in real workloads.

Key question: "Does this affect proofs generated by real provers (leanMultisig, SP1)?"

## Your Task

Read the Plonky3 source — start with `monty-31/src/`, `baby-bear/src/`, `dft/src/`.
Understand the Montgomery representation, how packed SIMD ops are implemented, how
the DFT composes with field arithmetic.

Then form your own hypotheses about what could go wrong. Build your own investigation

bugs through code analysis, prove them with a reproducing test, and fix them.

## Iteration Loop

1. Read code. Reason about invariants, edge cases, unsafe blocks, cross-crate assumptions.
2. When you spot a suspicious pattern: convince yourself it's a real bug by tracing
   the logic. Don't write a test for every hunch — only when you believe you found something.
3. Write a minimal reproducing test that demonstrates the bug.
4. `git commit` the test: `hunt-<id>: <hypothesis summary>`
5. Run the test. **Always use** `RUSTFLAGS="-C target-cpu=native"` — without it, no AVX-512 and SIMD paths won't be exercised.
   - **Test fails (bug confirmed):** Write a fix. `git commit`: `hunt-<id>-fix: <description>`.
     Re-run the test to verify it passes. Log in findings.tsv.
   - **Test passes (bug not real):** `git revert HEAD` to remove the useless test.
     Log as `not_found` in findings.tsv with your reasoning.
6. Move to next area of the codebase.

If after analysis you conclude a pattern is safe without needing a test, log it as
`not_found` in findings.tsv with your reasoning.

**Commit discipline:** Every reproducing test and every fix gets its own commit.
Reverts use `git revert`, not `git reset`. This produces a linear, reviewable history.

**If something fails unexpectedly:** Log the error and move on. Do NOT spend more
than 15 minutes on infrastructure problems. Report back if blocked.
